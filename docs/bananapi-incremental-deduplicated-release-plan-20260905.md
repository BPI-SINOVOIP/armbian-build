## 四、唯一鍵與防重規則

映像用途唯一鍵為：

```text
folder / board / branch / release / profile
```

候選建置身分另包含：

```text
source_commit
bsp_base_commit
matrix_sha256
userpatches_sha256
build_context_sha256
```

執行規則如下：

1. 候選項目必須符合固定的來源提交與建置內容雜湊，並具有完成標記、映像、
   同名 SHA 檔及雜湊一致的受控完整日誌，才算本輪完成。
2. 完整候選板必須具有所有預期項目與板級完成標記，才可直接進入整板發布驗證。
3. 部分候選逐項保留；完成該板時只能建置帳本所列缺項，不得整板重來。
4. 既有正式板是可回復基線，不是本輪最新來源成果，不能抵銷本輪待辦。
5. 待辦佇列以外的唯一鍵不得呼叫 `compile.sh`。
6. 每次呼叫建置前重新掃描；若狀態已不是「本輪缺少」，立即停止該項。
7. 每個建置嘗試使用獨立 UUID 日誌，不覆寫先前成功或失敗紀錄。
8. Armbian 內部建置日誌複製到受控狀態目錄並記錄 SHA-256，不依賴會被框架
   輪替的 `output/logs` 原路徑。
   既有 94 個項目則使用已驗證雜湊的完整主日誌，不因內部副本已輪替而重建。
9. 中斷交易若已恢復為完整板，立即返回，不得再次進入映像建置迴圈。
10. 未明確指定板卡時，重建工具預設拒絕執行全矩陣；只有人工明確允許才可解除。

## 五、同類映像順序與分工

實際待建為 350 個項目。映像編譯只允許一個主工作，避免多個容器爭用 Kernel、
Bootloader、套件快取、迴圈裝置與磁碟；XZ 壓縮則交由另一個單一工作並行處理。
映像編譯的固定優先序如下：

```text
架構 → 發行版 → 映像類型 → 元件 family → 板卡
```

| 執行架構 | Armbian `ARCH` | 板卡數 |
|---|---|---:|
| `arm32` | `armhf` | 16 |
| `arm64` | `arm64` | 26 |
| `riscv64` | `riscv64` | 3 |

架構固定為 `arm32`、`arm64`、`riscv64`。各架構先完成同一發行版的所有板卡，
再切換下一個發行版；同一發行版先完成全部 `minimal`，再完成全部 `xfce`。
發行版固定順序如下：

1. `trixie`
2. `bookworm`
3. `jammy`
4. `noble`
5. `resolute`

架構與 family 順序固定於 `config/bananapi-latest-build-groups.tsv`，且必須與
`config/bananapi-latest-release-matrix.tsv` 的 45 塊板一一相符。八塊已完成板只做
整板驗證與發布；三塊部分完成板沿用既有項目並補缺；其餘板才執行完整板組。
不能只用板名或 `current`、`legacy`、`vendor`、`edge` 推論架構或共用核心。

### 編譯與壓縮管線

1. 主工作呼叫 `compile.sh`，只要求產生 `.img` 與原始 SHA-256，不在該工作內
   執行 XZ。
2. 原始映像通過唯讀內容檢查後，先寫入可恢復的 `handoff` 標記，再移到受控
   原始映像目錄，最後以原子改名轉成 `ready` 標記。
3. 只要 `ready` 標記落盤，主工作即繼續下一塊板或下一個 OS，不等待 XZ。
4. 獨立壓縮工作把 `ready` 原子改為 `compressing`，重新計算原始 SHA-256，
   產生 `.img.xz`，執行 `xz -t`，再產生壓縮檔 SHA-256 與項目完成標記。
5. 若程序中斷，`handoff` 由下一次建置呼叫恢復，`ready` 與 `compressing` 由
   壓縮工作續作；這三種狀態都不得重新編譯。
6. 原始映像佇列預設最多四個，磁碟可用空間不得低於 40 GiB。超過任一限制時，
   主工作只等待壓縮釋放容量，不再啟動新的映像編譯。
7. 建置清單是啟動時的快照，但每項開始前仍重跑帳本；已完成或已待壓縮者直接
   跳過，避免中斷續跑或外部成果匯入造成重複工作。

## 六、收斂流程

1. 重新執行盤點，固定本輪來源提交、建置內容雜湊與 444 列帳本。
2. 完整重驗 94 個候選映像，不重新編譯；具有全部項目的板只補整板驗證。
3. 啟動單一壓縮工作，先接手任何中斷前已存在的原始映像。
4. 依架構、OS、類型、family、板卡順序，只建置帳本中的缺少項目；每個原始
   映像交付壓縮佇列後立刻繼續下一項。
5. 主工作完成所有 `.img` 後送出結束訊號，等待壓縮佇列清空，不得遺留
   `handoff`、`ready` 或 `compressing` 標記。
6. 逐板執行映像數量、檔名、SHA-256、XZ 串流與唯讀內容驗證，再以可回復交易
   安裝候選板目錄；驗證失敗不得取代既有正式板。
7. 每次狀態轉換後重跑盤點；待編譯數只能下降，待壓縮數最終必須歸零。
8. 全部完成後，正式區逐項驗證檔名、板卡、分支、發行版、類型、SHA-256、
   XZ 串流與映像唯讀內容，數量必須是 45／444／444。
9. 全域驗證成功後才封存 R1，並依清冊移除中止產物、空白暫存目錄與舊別名。
