## 2. 需求理解與完成目標

真正的阻礙不是 AI 原理上不能寫 SD，而是 SD 插在待測板時，主機無法像插卡讀卡機一樣直接更新它；待測系統又可能在 DDR 初始化時就失敗。人員不在場時，不能持續拔卡、重燒、插卡及上電。

目標是一張預先部署好的實驗 SD：固定救援入口可以透過 UART 接受命令，選擇 DDR 測試程式、不同 SPL2、更新模式或不同 OS。主機透過既有電源控制，在實驗失敗後自行重新進入救援入口，繼續下一個受控測試。

| 使用情境 | 預期操作 | 不再需要的重複操作 |
| --- | --- | --- |
| DDR 參數調校 | 主機送出受限參數設定，冷啟動測試並收集結果 | 每組參數重新編譯、拔卡與重燒整張 OS |
| 更換 DDR 初始化流程 | 更新非使用中的 SPL2 槽，再一次性試跑 | 覆寫唯一的 BootROM 啟動入口 |
| 更新 SPL／ATF／U-Boot | 驗證完整組合後選擇對應槽 | 每次重新製作整套根檔案系統 |
| 比較 kernel 6.6.75 與其他版本 | 選擇各自完整的核心、DTB、模組及根檔案系統 | 手動交換多張 SD，或混用不相容元件 |
| 初始化失敗或沒有 UART 輸出 | 主機逾時後重新上電，回到 SRAM 救援 | 等待人員拔卡處理一般實驗失敗 |

完成標準不是「可以顯示選單」，而是首次部署後，主機能完成更新、驗證、一次性試跑、判斷失敗及復原；每一步都有可追溯證據。未經額外核准，不刪除既有映像、原始紀錄或客戶使用中的環境。

## 3. 已查核的基礎與缺口

### 3.1 目前已具備的能力

- 整合分支已有免重新編譯的 DDR 調參實作，見[既有 DDR 實驗計劃](bananapi-m4zero-ddr-lab-plan-20260813.md)及[操作文件](bananapi-m4zero-ddr-lab-guide-20260813.md)。目前可下發時脈、驅動強度、ODT、部分 TPR 與測試設定，不必重新發明這些介面。
- D1 已實際交叉編譯，並在 0845 的兩輪啟動中執行 SRAM 堆疊診斷。UART 接收及主機控制電源已有實驗紀錄，可重用工具，但不在本文重新操作硬體。
- 本地 D1 所用 U-Boot 2024.04 的 `drivers/mmc/sunxi_mmc.c` 有 `mmc_trans_data_by_cpu()`。這是 SRAM 分塊讀寫的可用起點，不代表整條 MMC 初始化路徑、配置器或全域資料已脫離 DRAM。

### 3.2 不能直接沿用的假設

- D1 的 SRAM 隔離從 `jump_to_image_no_args` 才開始。在此之前的 DDR 初始化、MMC／FIT 載入仍可能先失敗，不能直接把 D1 改名為救援管理器。
- D1 建置仍有 `CONFIG_SPL_STACK_R=y`，重定位堆疊位於 DRAM，BSS 亦位於 DRAM；`CONFIG_SPL_MMC_WRITE` 未啟用。新管理器必須重新稽核從入口開始的全部程式、BSS、堆疊、配置器與 I/O 緩衝。
- D1 的 40 KiB 媒體槽中，裸 SPL 與標頭後只餘 1184 位元組。不能把選單、更新器直接附加進目前槽內；需要新的實驗卡配置及獨立建置目標。
- D1 兩輪 SRAM 診斷均觀察到同址重讀不一致，但使用的是 C0 舊版 792 MHz 參數，不是 A1；尚不能確認根因或宣告任何一版對 0845 長期穩定。
- U0 480 MHz、A1 792 MHz、舊版 6.6.75 等均只能依各自板號、批次與證據列為回退候選。曾進入 Linux 不等於可作所有板子的通用安全版本。
- 舊 DDR 實驗器先經 `sunxi_board_init()` 才進入 UART 迴圈；每輪結束又要求 `lab_safe` 初始化成功。它不等於 DDR 失敗時仍可用的入口，而且獨立實驗建置刻意關閉 MMC／FIT 載入。

## 4. 建議架構

```text
SoC BootROM
  -> 固定 SPL1：SRAM 啟動管理器，不初始化實驗 DDR
       -> UART 握手／查詢／一次性選槽
       -> SPL-UPDATE：SRAM 更新器
       -> SPL2：DDR 測試槽
       -> SPL2：經驗證的回退啟動槽
       -> SPL2：實驗啟動槽
            -> 配套 ATF／U-Boot／DTB
                 -> 各自的 kernel／initrd／模組／rootfs

實驗逾時或失敗
  -> 看門狗或主機電源循環
  -> 重新執行固定 SPL1
  -> 不自動重跑剛才的實驗槽
```

### 4.1 SPL1：最小、固定、獨立於 DDR 的救援入口

1. 從 BootROM 入口開始只使用已核對的 SRAM，初始化最低限度 UART、時基及必要時脈；不使用實驗 DDR 設定。
2. 支援機器可解析的握手、版本及能力查詢、合法槽位選擇，以及有長度與位址界限的 UART RAM 載入。每次複製都檢查界限；跳轉前核對最終 SRAM 內容的長度、SHA-256、ABI 與入口，連同 BSS／堆疊需求檢查，不只相信主機已選對檔案。
3. 先提供 UART 握手，再按命令使用受限、唯讀的 SD 路徑載入更新器或 SPL2。SD 初始化／讀取逾時或中繼資料損壞，必須有界返回可接收 UART RAM 載入的狀態，不反覆卡在自動讀卡流程。此能力以 BootROM 已成功載入 SPL1 為前提，不涵蓋整張卡無法讀取。
4. 不加入檔案系統、網路、圖形選單或任意記憶體／磁碟寫入命令；如大小超限，先縮小功能並重新討論，不暗中改為依賴 DDR。
5. 第一版預設停留在救援命令狀態。無主機時可等待，不因逾時自行試跑未知版本；自動啟動已核准安全槽屬後續可選政策。
6. 日常更新不得改寫 SPL1 或 BootROM 保留區。SPL1 自身升級屬獨立維護操作，需要備份、回復媒體及另行核准。

### 4.2 SPL-UPDATE：不需要 Linux 的 SRAM 更新器

1. 正常由 SPL1 從固定更新器副本載入；兩份都無效時，可由 UART 直接載入 SRAM 執行。
2. 使用已稽核的 SRAM 程式、堆疊、BSS 及固定大小緩衝，以 CPU／PIO 路徑分塊存取 SD，不要求把整個映像放入 DDR。
3. 一般資料寫入僅允許指定的非使用中實驗槽或可替換更新器槽；中繼資料另提供固定格式、固定區域的交易提交操作，只能寫非目前有效副本。拒絕 SPL1、分割表、保留區、安全槽及超出範圍的寫入，不提供任意 LBA 例外。
4. 先完成資料傳輸、整體雜湊與媒體讀回，再提交新中繼資料；中途失敗不得改變目前有效啟動組合。
5. 更新器本身使用分開的副本，更新時不覆蓋最後一份已核准可用副本；從 UART 載入的更新器同樣必須符合主機允許清單。

### 4.3 SPL2：可替換的 DDR 與啟動實驗

- 分成「只做 DDR 初始化／測試」及「初始化後載入完整啟動組合」兩種工作，不強迫每次進 Linux。
- 已支援的時序、驅動強度、ODT、訓練選項及測試參數，改由版本化設定結構傳入；程式流程有改變時才重新編譯 SPL2。
- 參數只能使用已定義欄位、範圍及相容性規則；不能把任意 MMIO 位址／數值當作一般調參介面，也不開放未經供電規格核准的電壓掃描。
- DDR 初始化／重初始化期間，所有執行程式、堆疊、結果緩衝與控制資料必須留在 SRAM，並停止可能使用 DDR 的 DMA／其他主體。
- 首版每組破壞性 DDR 參數使用真正的重新上電；不依賴實驗程式返回 SPL1，也不把暖重啟當成完整冷啟動。

## 5. SRAM 配置與交接契約

TF-A 的 H616 平台定義提供 SRAM A1 `[0x20000, 0x28000)`，32 KiB，以及 SRAM C `[0x28000, 0x58000)`，192 KiB。這是配置起點，不代表全部空間可同時交給本專案；BootROM 上下文、其他韌體及交接階段使用範圍須另行核對。[來源：TF-A v2.12.0 平台定義](https://github.com/ARM-software/arm-trusted-firmware/blob/v2.12.0/plat/allwinner/sun50i_h616/include/sunxi_mmap.h)

首版配置採分時使用：SPL1 保留控制區，SPL-UPDATE 與 SPL2 使用同一個受控載入區，兩者不並存執行。最終位址與大小在 P1 決定，必須由連結映射、反組譯、堆疊估算與實板證據共同核對，不能先寫死猜測值。

| 必須定義的交接項目 | 要求 |
| --- | --- |
| 版本與識別 | ABI 版本、結構長度、SoC／板型／DDR 設定識別、啟動工作識別與雜湊 |
| CPU 狀態 | 指令集、EL、SP、例外向量、遮罩、MMU／快取及屏障政策均明確；不得繼承未知狀態 |
| 記憶體所有權 | 程式、BSS、堆疊、UART／SD 緩衝、上下文及哨兵不重疊；不能解參考上一階段的失效 `gd` |
| 裝置狀態 | UART、時基、時脈、SD 控制器及 DMA 的保留／重新初始化政策 |
| 媒體來源 | 開機裝置、卡片身分檢查、槽範圍及配套 FIT／元件的確切位置 |
| 交接生命週期 | SPL2 接手後不承諾返回；ATF 目的區若與載入器重疊，必須在寫入第一個重疊位元組前，搬移所有存活程式、堆疊、資料及讀取路徑，或使用已驗證的搬移跳板 |

驗收須包含逐階段的記憶體生命週期圖，不只比較各個映像靜態大小；載入中與交接中也不能發生自我覆寫。SPL1 保留區與可載入 SRAM 範圍由固定規格限制，不由 SD 上的可變描述擴張。

不能直接用 `go` 跳進任意舊 SPL 或原廠 boot0。舊程式可能固定連結位址、重新清除 BSS、依賴 eGON／BootROM 上下文，甚至覆蓋 SPL1 自己的堆疊。首版只支援依契約重新建置的 SPL2；原樣舊二進位的搬移跳板與相容層另設研究項目。

尤其要改造後續載入位置的傳遞：目前 sunxi 路徑會依 SPL 標頭長度及開機位置推算 U-Boot／FIT 的扇區。把 SPL2 放進新槽並不會自動讓它載入該槽配套的 FIT；必須顯式傳入並驗證槽資訊，不能讀回舊的固定位置。[來源：U-Boot 的大於 32 KiB SPL 載入修正](https://github.com/u-boot/u-boot/commit/c0b417b2f1)

## 6. SD 多槽與多系統配置

### 6.1 初次部署

建議用另一張專用實驗 SD 完成一次初始部署，保留目前對照卡與完整備份。現有卡曾擴展根分割區，不能假定尾端有空間，也不能直接縮小或重新分割正在使用的卡。

初次部署仍需要將目標 SD 接到可寫入的設備一次。部署前核對實際裝置身分、容量、掛載、分割表、BootROM 區域及整卡備份；之後才追求日常測試零拔卡。此授權尚未包含在本次文件工作內。

### 6.2 邏輯區域

| 區域 | 內容 | 日常更新政策 |
| --- | --- | --- |
| BootROM 保留區 | SPL1 與必要的啟動標頭；可能的替代 ROM 探測區也必須保留 | 禁止日常工具寫入 |
| 固定描述區 | 格式版本、布局識別、容量與區域界限 | 只有初始部署／專項維護可改 |
| 中繼資料 A／B | 世代、完整啟動組合清單、長度、雜湊與提交狀態 | 只寫非目前有效副本 |
| 更新器 A／B | 經核准的 SRAM 更新器 | 保留至少一份已驗證副本 |
| 安全候選／已核准安全槽 | 固定 SPL2 及配套韌體；狀態由板級驗證決定 | 一般試驗禁止覆寫或自動晉升 |
| 實驗槽 A／B／其他槽 | DDR 測試或啟動組合 | 只更新非使用中且未被保留的槽 |
| 系統區域 | 多份 kernel／initrd／DTB／模組／rootfs | 各自完整配套，獨立可寫區 |
| 結果區域 | 可選的板端測試紀錄 | 不作唯一證據；主機持續封存 |

上表不是燒錄偏移表。正式 LBA、對齊、最大映像大小與分割方式必須在 P1 凍結並產生機器可檢查的布局描述，更新器與主機共用同一份規格。

### 6.3 分割表與 ROM 的限制

sunxi 的傳統 8 KiB 啟動位置會與常見主 GPT 分割項陣列重疊。以 512 位元組扇區、從 LBA 2 起放置 128 筆各 128 位元組的 GPT 項目計算，陣列佔 LBA 2 至 33，包含 SPL 的 LBA 16。[來源：linux-sunxi 原專案布局文件](https://linux-sunxi.org/index.php?title=Bootable_SD_card&oldid=26799)

H616 的替代位置是 256 KiB／LBA 512，不是其他 SoC 常見的 128 KiB；上游修正與本地 D1 原始碼均有對應處理，H618 另有上述原專案文件佐證。首版仍須實板驗證實際 ROM 路徑；有效主 SPL 執行後卡死，不能指望 BootROM 自動轉向替代位置。[來源：2024-05-10 上游修正](https://lists.u-boot-project.org/pipermail/u-boot/2024-May/553283.html)

首版優先採已核對的 sunxi 相容 MBR 配置。超過四個根分割區時，須驗證延伸／邏輯分割區與各版 U-Boot／Linux 的支援；若改採 GPT，必須先證明高位啟動、保留區及全部啟動鏈相容，不能套用一般 GPT 工具的預設布局。

### 6.4 每一槽是一個完整組合

每個可開機設定至少綁定 `SPL2 + DDR 設定 + ATF + U-Boot + kernel + DTB + initrd + modules + rootfs`，包含各元件來源提交、長度、SHA-256、板型、ABI 及根分割區識別。不要把某個 6.6.75 核心與新版本模組、DTB 任意搭配。

不同系統使用唯一 UUID／PARTUUID，不共享可變的安全根目錄。首次擴容、安裝到 eMMC、bootloader 套件升級及 Armbian 寫入啟動區的服務，必須在實驗卡專用設定內停用或加守門，不能讓進入 Linux 後的自動操作覆寫 SPL1 或其他槽。

每槽須隔離或固定 U-Boot 環境、`bootcmd`、`extlinux.conf`／`boot.scr` 與掃描目標，並核對實際根分割區及核心識別。元件缺失時回到救援，不自動從其他槽、eMMC 或 USB 補找系統。原始 rootfs 映像雜湊用於部署驗證；可寫根目錄開機後會變動，必須另記錄變動政策，不把它當成每次開機都不變的二進位。

實驗卡不得直接當作一般客戶發布映像。正式發布仍使用正常單系統布局；實驗架構及其限制須明確標示。

## 7. UART 控制與資料傳輸

### 7.1 採成熟傳輸協定，限定控制介面

- 控制面提供查詢、列槽、準備更新、驗證、一次性執行及取消等固定操作；命令名稱與格式在 P1 定案，目前沒有可執行的新 CLI。
- 資料面優先評估既有 YMODEM 實作，再加入槽範圍與整體完整性檢查。U-Boot 主程式的 `loady` 與 SPL 的 `spl_ymodem_load_image()` 是不同入口，後者也只是記憶體載入路徑，不是 SD 更新交易；必須改造成受限 SRAM 串流接收，不直接接受映像標頭指定的任意載入位址。[來源：v2024.04 載入命令](https://docs.u-boot.org/en/v2024.04/usage/cmd/loady.html)、[SPL YMODEM 原始碼](https://github.com/u-boot/u-boot/blob/v2024.04/common/spl/spl_ymodem.c)
- 二進位傳輸期間不得混入一般日誌；狀態機明確處理文字／資料模式切換、逾時、取消、重送及主機重新連線。
- 傳輸區塊校驗不取代完整映像 SHA-256 與寫入後讀回。協定重送也不等於斷電後自動續傳；首版可安全重傳整個非使用中槽，分塊持久續傳另作測試後才啟用。
- 主機指定新的工作識別與隨機挑戰值，裝置回覆版本、能力及本次回顯；只用於對應這輪工作與避免舊日誌誤判，不宣稱可驗證不可信實驗韌體的真實身分。

### 7.2 UART 頻寬的實際限制

`115200`、`8N1` 的理想上限為每秒 11520 位元組，尚未扣除協定與媒體寫入成本：

| 資料量 | 理想最短時間 |
| --- | --- |
| 40 KiB SPL | 約 3.6 秒 |
| 1 MiB 元件 | 約 91 秒 |
| 1 GiB 映像 | 約 25.9 小時 |

因此預設以 UART 更新 SPL／參數等小元件，多套 OS 在初次部署時先放好。後續大檔優先透過已驗證安全系統的網路或 USB 更新；如板子、連線與 BootROM 支援條件成立，再評估 FEL。提高到 `921600` 等速率必須先做線材／橋接器長時間驗證，不當作目前已可用能力。

## 8. 更新交易、回退與保護界線

### 8.1 更新交易順序

1. 主機與 SPL-UPDATE 核對布局版本、板型、映像大小、目標非使用中槽及目前有效組合。
2. 保持目前組合及舊中繼資料不變，只寫入允許的目標區域；每個 I/O 等待都必須有界限。
3. 完成傳輸、SD 狀態確認及整體讀回 SHA-256，比對主機預期值；先不切換預設啟動。
4. 建立新世代描述，確認它引用的所有元件均已完整寫入，再寫入非有效中繼資料副本並讀回校驗。
5. 重新進入 SPL1，以一次性指令測試新組合；通過所要求的板級測試後，才由主機記錄可用狀態。
6. 改變長期預設或提升安全槽需獨立核准，不能只看實驗韌體自行列印的通過字串。

中繼資料至少包含格式版本、結構長度、布局識別、世代、槽範圍、元件雜湊與校驗。解析需防整數溢位、越界、重疊及版本不相容；兩份都不合法時，留在 UART 救援，不猜測任意槽。

有效描述必須同時通過結構、完整內容校驗與完成標記檢查，不能單憑世代較大就接受。世代採不回繞計數；同世代同內容視為副本，同世代不同內容視為衝突並留在救援。兩份皆有效時優先核對較新世代，執行前仍重驗所選啟動元件；元件不符則回救援，由主機明確選擇經重驗的舊組合。完成標記的實際寫入／失效順序與讀回規則在 P1 凍結，P3 證明其斷電行為，不能假定單扇區寫入天然原子化。

「非使用中」不只表示目前 CPU 沒在執行。任何仍被已保留的啟動描述、回退組合或未結束試驗引用的元件都不可覆寫；回收前先解除引用並驗證新描述有效。空間不足就停止更新，不能刪除最後可用組合騰位。

解除引用須完成兩份描述的受控輪替與讀回，使全部保留的有效描述都不再引用待回收槽，才可重新使用它；中斷時從實際有效描述重建引用集合，不只沿用主機記憶體中的判斷。P3 必須測試連續兩次更新途中斷電及舊描述復原，避免只通過第一次空槽更新。

保留區與最大可寫範圍由更新器內建的已核准布局界限約束，不接受可變中繼資料任意放寬。檢查包括扇區取整後的實際 I/O 範圍，不只檔案位元組範圍。固定描述區損壞時，UART 仍可載入更新器，但只能在主機核對原始部署清單、卡片與布局後進入受限修復；不能把修復模式變成任意磁碟寫入。

### 8.2 回退的實際機制

首版每次重啟都回到 SPL1 的救援狀態，實驗選擇只在該輪有效。這能先避免持久 bootcount 寫入與卡在壞版本的循環；主機的工作紀錄負責有限次重試。未來若增加自動 A／B 開機，才引入經斷電測試的次數與成功確認機制。

片上看門狗只是第一道恢復手段。實驗碼可能停用它或令系統匯流排失常，仍需主機使用既有電源工具。插座回報斷電不等於板上電源軌歸零，必須排查 UART／USB／HDMI 回供電；冷啟動條件不成立的輪次不能算入冷開機驗收。

### 8.3 不承諾的事情

- SD 的 FTL、寫入快取及斷電行為不能由 A／B、CRC 或 SHA-256 自動保證原子性；不同副本甚至可能位於同一實體抹除區。必須在指定卡型上做斷電故障注入，結論不無限制外推。
- SPL1 與安全槽的禁止寫入，首版屬工具與流程限制，不是硬體寫入保護。高權限錯誤／惡意 SPL2 或 Linux 仍可能破壞整張 SD。
- 雜湊是完整性檢查，不是簽章或可信啟動。首版限定受控實驗室與已授權實體 UART；需要防惡意更新時另做簽章、金鑰與硬體信任根設計。
- SPL1 損壞、SD 故障、電源／UART 連線損壞、主機失聯或無法消除回供電，仍可能需要人工換卡／接線／維修。不得對外宣稱永遠不會無法啟動。

## 9. 主機自主測試與防止重做

主機沿用既有 UART、DDR 測試及電源控制工具，新增明確狀態機，不從實驗日誌執行任何命令。操作前先取得裝置排他鎖，依固定設備登錄表配對板號、UART 與電源，不探測或切換無關設備。

序列埠以實際 USB 拓樸及設備資訊核對，不只依賴會變動的 `ttyUSB0` 編號，也不能只依賴可能重複的轉接器序號。自動化 HID 裝置與其他板子的電源不在允許範圍。

```text
載入工作紀錄並核對設備
  -> 啟動 UART 收集
  -> 受控斷電等待／上電
  -> SPL1 握手及本輪識別
  -> 必要時更新非使用中槽並讀回驗證
  -> 一次性執行測試
  -> 收集結果或逾時分類
  -> 主機封存原始資料與判定
  -> 按有限重試／停止規則進入下一輪
```

紀錄至少包含板號／DDR 批次、映像與設定雜湊、來源提交、布局、工具版本、工作識別、每次電源事件、UART 原始檔雜湊、各階段時間、測試範圍與結論。測試狀態區分未執行、執行中、通過、失敗、證據不足及等待人工。

恢復工作時以紀錄與實際槽雜湊共同核對。清單分開記錄設定識別、輪次識別、要求樣本數及有效完成數，只跳過已完整封存的指定輪次，不跳過仍欠缺的冷啟動或故障注入樣本。條件改變建立新工作；主機中斷、日誌缺失或無輸出不能當作通過，也不能計入已完成樣本。

預設同一工作連續三次無握手／不可判讀就停止該設備的自動重啟，保留最後狀態並列出原因，不無限斷電。過熱、供電異常或設備身分不符立即停止；停止政策及各階段逾時須在部署前凍結。

P1 另定義冷啟動、溫度與供電的可觀測來源、門檻及訊號失聯政策，不能依賴待測 Linux 或不穩定 DDR 才取得安全資訊。沒有獨立量測時，只能使用已驗證的接線／治具條件及受限工作範圍，明列未覆蓋的保護；新增感測器或接線另行核准。未具備必要觀測條件的自動壓力測試不得啟動。

## 10. 選項比較與採用理由

| 作法 | 適用情境 | 本次取捨 |
| --- | --- | --- |
| 安全 U-Boot／Linux 選不同 OS | DDR 已穩定，主要驗證核心及使用者空間 | 保留為快速更新通道；不足以救援 DDR 初始化失敗 |
| 固定 SRAM SPL1、可換 SPL2／更新器 | DDR、SPL、核心都可能需要實驗 | 本案主線；先證明 SRAM 與 SD 路徑，再擴大功能 |
| BootROM FEL | USB 資料線與進入模式均可遠端控制 | 備援研究；不假定現有 UART／電源接線就能使用 |
| 原樣串接任意舊 SPL／boot0 | 需要精確重建各自入口與媒體假設 | 非首版承諾；先支援有明確 ABI 的可重新編譯 SPL2 |

成熟的多階段載入、序列埠傳輸與 A／B 思路值得沿用，但名稱相似不代表 H618 已有完整、無 DDR 依賴的組合。具體採用哪些上游模組，以容量與依賴審查結果決定。

U-Boot v2024.04 文件已有 TPL／VPL／SPL 分工，且明示 VPL 的選擇邏輯尚在開發，不能把啟用它當成本案已完成。P1 應評估採用 TPL／SPL 的建置方式或獨立 SPL 設定，保留共享驅動；本文不預先承諾只切換 Kconfig 即可完成。[來源：固定版本 xPL 文件](https://docs.u-boot.org/en/v2024.04/develop/spl.html)

## 11. 分階段實施、交付與驗收

每一階段先完成本機確定性測試，再進入該階段需要的實板驗證。沒有對應硬體證據，不把編譯或模型通過寫成實板通過。這次僅執行 P0。

| 階段 | 交付 | 必須通過的門檻 | 目前狀態 |
| --- | --- | --- | --- |
| P0 | 本計劃、來源核對、獨立分支及推送 | 文件審查；確認不觸及韌體與原始證據；等待使用者討論 | 文件審查完成；推送以本分支遠端提交為準，實作待討論 |
| P1 | 凍結來源／工具鏈、SRAM 映射、ABI、媒體布局及風險清單 | 所有入口依賴可追蹤；無區域重疊；確認首次部署與回復方案 | 未開始 |
| P2 | 最小 SPL1、UART RAM 載入與無 DDR 的 SD 唯讀載入 | 完全略過 DDR 初始化仍可握手及載入；SD 初始化／讀取逾時、壞描述後仍有界回到 UART；全部狀態位於 SRAM | 未開始 |
| P3 | SRAM SPL-UPDATE、槽位工具、交易中繼資料 | 分塊寫入與讀回一致；錯誤輸入拒絕；斷電後可回救援；不更動受保護區 | 未開始 |
| P4 | 可重新建置的 SPL2、既有 DDR 工具與參數結構移植 | 相同二進位可換受限參數；故意失敗後主機復原；測試自身不依賴 DDR | 未開始 |
| P5 | 配套啟動槽、回退候選及多 OS 選擇 | 至少兩個完整系統可選，含 6.6.75 對照；根分割區及模組不混用；自動服務不越界寫入 | 未開始 |
| P6 | 無人值守狀態機、可續接工作紀錄及硬體故障注入 | 達成下方量化驗收；證據完整；停止與人工交接可靠 | 未開始 |
| P7 | 操作／復原文件、可重建套件及後續平台介面 | 指定板型驗收通過；授權清單與限制清楚；再另議 M4 Berry 及其他 SoC | 未開始 |

P1 建置基準須同時保留上游 U-Boot 提交、BPI 修補集、工具鏈版本與雜湊。先移植一個窄範圍可重現目標，不直接重新改寫所有 Banana Pi 的啟動鏈；實驗功能預設關閉，不影響現有正常映像。

P2 若超出 SRAM 或 BootROM 可載入限制，需回報具體連結映射與減項方案；不得將 SRAM A1／C 總容量當成 BootROM 必然接受的單一映像上限。P3 未通過前不依賴遠端更新作唯一復原方式。

### 11.1 初始量化驗收提案

- 對每個宣稱支援的板型／DDR 批次，執行至少 100 次符合供電條件的救援冷啟動，UART 握手零遺失；回供電未排除者另列，不能混算。
- 每個已識別的更新寫入／提交故障窗口至少做 20 次中斷測試，包含資料傳輸、資料寫入、讀回、描述寫入及提交；中斷位置與亂數種子留存。這是實驗驗收，不是所有 SD 的原子性證明。
- 覆蓋壞 CRC／雜湊、過大／截斷包、錯板型、錯 ABI、越界與重疊槽、兩份中繼資料皆壞、更新器皆壞、UART 斷線／重複封包、主機中途停止等情境。
- UART 載入另測合法前綴後超量資料、取消／截斷後誤執行及 SRAM 內容不符；中繼資料另測同世代衝突與連續更新中斷。每種拒絕都不得破壞既有可用組合。
- 系統選槽故意保留另一槽的可開機設定、污染共用環境並移除本槽核心，確認不會啟動錯誤 OS 卻記錄為本槽成功。
- 故意讓 SPL2 在 DDR 初始化前後停止、關閉看門狗或沒有日誌，仍能由主機控制電源回到 SPL1；禁止以 SPL2 正常返回模擬這項驗收。
- 連續至少 24 小時無人操作，完成更新、至少兩套 OS 切換及故障回退；除初次部署外零拔卡，所有工作可從主機紀錄重建。
- DDR 的正確性另以受控圖樣、全容量／地址覆蓋、訓練餘裕、冷熱啟動與長時間負載驗證，要求受測範圍零錯誤；本架構驗收不取代 DDR 校準或量產可靠度驗證。

## 13. 討論時需要確認的決策
