# H618 多板識別、多系統救援與網路驗證整合計劃

日期：2026-09-15。工作分支：`bpi-h618-recovery-network-20260915`。

## 1. 需求與執行順序

將這幾輪關於 SPL1／SPL2／SPL-UPDATE、共用映像、HW_ID、SD／eMMC、UART、外部電源與 PXE 的討論集中保存，供其他開發者與人工智慧接續。先提交並確認遠端推送成功，再進行新增工具與設備驗證。不修改 `main`，不直接把實驗內容合併至 `bpi-integration-20260829`。

目標是減少人工拔插 SD 及陪同除錯：一次受控部署專用救援卡後，由主機選擇軟體、傳輸產物、收集證據及在確認配對後控制冷啟動。不是宣稱所有故障皆能軟體復原，也不是把離線測試當成 DDR 或量產驗收。

本輪核准範圍為計劃保存、主機端離線工具及對已知候選設備的唯讀盤點。實際改寫 SD／eMMC、重開機、UART 接管及電源切換，須先核對目前設備配對和各階段部署條件；不得沿用歷史板號或授權猜測操作對象。

## 3. 討論決策紀錄

| 主題 | 採用方向 | 不得誤解的限制 |
| --- | --- | --- |
| 減少人工插卡 | 固定 SRAM 救援入口，加上可選 SPL2、更新器與安全系統 | 第一次部署仍可能需要人工；物理壞卡或 BootROM 無法載入第一層時，UART 菜單也到不了 |
| 一份映像多板使用 | 先限定 M4 Zero、M4 Zero EMAC、M4 Berry；共用交付包、相容核心與使用者空間，保留各板啟動配置 | 同為 ARM64 或 H618 不代表電源、DDR、腳位及 DTB 可直接混用 |
| 準確識別 | PCB／BOM 核對、HW_ID 實測、SID 登記與明確的擴充配置 | 軟體 DT 名稱、MAC、eMMC 廠商、Wi-Fi 或記憶體容量均不能單獨證明實體板型 |
| 原廠 BSP | 參考分板配置、通用 LRADC 讀值及啟動封裝 | 尚未找到已啟用且完整的 Zero／Berry 自動選板實作；閉源 boot0 與廠內版仍有未知 |
| SD 與 eMMC | SD 留救援，eMMC 作受控試驗槽；板型選擇與系統槽選擇分開 | SD 載入 eMMC 的系統不等於 BootROM 原生 eMMC 冷啟動 |
| UART 與電源 | UART 作命令及日誌通道，已配對插座作外部重置 | 不把 UART 當大量映像傳輸通道；不能從舊對話直接操作插座 |
| 網路 | 先安全 Linux 下載，再 Berry 的 U-Boot 網路開機，最後 NFS 根檔案系統 | 不把 PXE 放進 SRAM 第一層；Linux 網路可用不等於 U-Boot 網路可用 |
| DDR 實驗 | 保留已知對照組，SPL2 在新 ABI 下測參數與邊界 | HW_ID 識別或能進 Linux，不代表 792 MHz 長時間穩定 |

## 4. 啟動架構

```text
BootROM
  -> 專用 SD 的固定 SPL1（SRAM）
     -> UART 選擇、來源及板型檢查
     -> 新 ABI 的 SRAM 測試／更新程式
     -> 選定 SPL2：DDR 初始化與早期測試
        -> 已配對 TF-A／U-Boot／DTB
           -> SD 安全系統
           -> eMMC 指定試驗槽
           -> 網路核心／DTB／initramfs -> 本地或 NFS 根檔案系統
```

上圖是目標架構，不代表現有原型已全部支援。不能以 `go` 直接跳入任意舊 SPL 或原廠 boot0：載入位址、例外層級、暫存器、時鐘、快取及交接 ABI 都須驗證。不同 TF-A、U-Boot、核心與保留記憶體亦須配套，避免重演先前映射衝突。

未知板或不確定 DDR 設定時停在 SRAM，等待明確選擇，不冒險啟動猜測的安全系統。已確認板型及救援組合後，試跑失敗才可退回該組合。

## 5. 板型、HW_ID 與擴充識別

1. 原理圖已有 HW_ID 接 LRADC 的線索，但 Zero 圖中的電阻標值與表格矛盾。先核對 PCB 版本、實裝 BOM、供電與量測點，不能現在寫死 ADC 門檻。
2. 確認 SRAM 階段可安全開啟 LRADC 所需時鐘與供電，且不改到其他板型的危險腳位，再實作原始值採樣。
3. 每個 PCB／BOM 類別至少三片，每片至少二十次冷啟動；保存多次原始採樣、離散程度、電源／溫度條件。以不重疊區間及保護區決定識別，落入保護區、漂移或超範圍即拒絕自動選擇。
4. SID 用來追蹤同片晶片；首次經實物核對登記 SID、板型、PCB 與 DDR 配置。SID 本身沒有可推導板名的既定表。
5. EMAC 初期視為 Zero 母板的顯式擴充配置。未確認存在 EEPROM 或專用在位腳前，不以主板 PHY 回應或網路連線狀態推定外接板存在。
6. 自動識別通過後才選取匹配 DTB／SPL2。人工選板僅限已有實物核對證據且配置在允許清單內的設備，仍須檢查 DDR 相容性並留下原因。證據未知或衝突時留在 SRAM；不得只憑人工覆寫理由執行 SPL2 或更新。

原理圖、來源提交及證據限制詳見[來源查核](bananapi-h618-recovery-network-sources-20260915.md)。

## 6. 儲存與復原規則

- SD 固定救援區、槽目錄、更新暫存區及系統分割區先做布局稽核，處理 H616／H618 的 BootROM 特例，不直接套用泛 sunxi 的備援偏移量。
- 保存原卡、來源映像、完整布局與必要備份；不覆寫 A1、C0、D1、6.6.75 或客戶對照卡。
- 每次試跑使用唯一工作識別及產物雜湊，交接前持久記錄「已消耗一次性試跑」。必須在重啟後仍可辨識，不能只靠 DRAM 變數。
- 元資料採兩份、世代編號、校驗及明確狀態機；先寫非啟用槽、完整回讀驗證，再提交選擇。各步驟斷電注入，不能假定單一磁區寫入具原子性。
- eMMC 寫入前重新核對控制器路徑、CID、容量、分割表、掛載與 swap 狀態。Linux 與 U-Boot 的 `mmc` 編號不得互相套用。
- 「非啟用槽更新」與「整碟映像燒錄」是不同操作。後者會取代分割表，不能承諾原 eMMC 槽或資料仍存在。
- 禁止日常修改 eMMC 開機分割區設定、RPMB、OTP／eFuse 或不可逆 EXT_CSD 欄位。
- SD 讀 eMMC 系統的測試與原生 eMMC 冷啟動分開報告。不以破壞 SD 開機標記強迫切換；必要時另設已驗證的 SD 隔離硬體，並檢查回灌電源。
- 安裝器、自動擴容及開機載入器套件升級不得越界改寫 SD 救援區。工具白名單與軟體唯讀不是硬體防寫，也不能抵禦有權限的任意程式。

## 7. 網路整合順序

### 7.1 安全 Linux 的資料傳輸

以現有已知候選 M4 Berry 開始，只讀確認目前系統與板型宣告。先記錄核心、DT 相容字串、SD／eMMC、掛載、網卡驅動與連線資訊，不執行燒錄、壓力測試、重啟或電源控制。

通過身分與救援可靠性確認後，再實作 HTTP(S)／SSH 下載、暫存、SHA-256 校驗及受控更新。DDR 不穩定時不進行大量解壓或媒體寫入。UART 保留給控制及日誌；115200、8N1 傳輸 1 GiB，理想下限也約 25.9 小時。

### 7.2 Berry 的 U-Boot 網路開機

逐一驗證網卡與 PHY、固定 IP 通訊、TFTP 傳輸校驗，再驗證 PXE。PXE 在已初始化 DRAM 的完整 U-Boot 執行，需要已核對的載入範圍與核心／DTB／initramfs 組合，並非 BootROM 原生網路啟動。[U-Boot PXE 文件](https://docs.u-boot.org/en/latest/usage/pxe.html)

不得在既有內網擅自啟動 DHCP 服務。初期用明確伺服器位址，後續採隔離網段或配合既有 DHCP 管理。主機雖有 TFTP 設定檔，仍須稽核其綁定位址、可寫設定、權限與使用者，不直接重用或修改既有服務。

工作選擇不得找不到指定項目就默默執行預設系統；失敗要記錄失敗，再退回本地救援。下載檔案與清單皆須限制大小和路徑；不執行任意遠端提供的 shell 或 U-Boot 指令。

### 7.3 NFS 與其他板型

先用本地根檔案系統隔離網路開機問題，再加入 NFS；每片板獨立可寫區，核心模組須與測試核心一致。網路驅動本身的壓力測試仍用本地根檔案系統，以免 NFS 故障混淆結果。[Linux NFS 根檔案系統文件](https://docs.kernel.org/admin-guide/nfs/nfsroot.html)

Zero EMAC 必須另驗 U-Boot 的 AC300／EMAC1 路徑；一般 Zero 可以評估 U-Boot 支援的 USB 網卡，但不假定 Wi-Fi 可供早期開機。網路啟動成功後，正式交付仍需回到本地映像及原生冷啟動測試。

## 8. 身分與產物契約

- 設備紀錄分開保存「軟體宣告板型」、「實物確認板型」、「HW_ID 量測」、「SID 登記」、「UART／電源配對」及證據日期。不得以其中一項代替其他項。
- 每個任務保存板型配置、測試槽、來源提交、產物路徑／大小／SHA-256、執行步驟與預期結果；未知板型、錯誤雜湊、缺漏或越界即拒絕。
- 第一版主機工具只做有限欄位的唯讀盤點及離線產物檢查，不提供燒錄或任意遠端命令功能。檢查通過不是執行授權，也不證明組件可啟動。
- 雜湊只能證明相對於可信清單的內容一致，清單與映像放在同一不可信伺服器並不構成來源認證。後續加入受信任清單簽章／FIT 驗證；本計劃不燒錄安全開機熔絲。
- 原始證據與實際設備清單存於忽略追蹤的 `output/evidence/`。公開文件只保留去識別摘要與雜湊，不推送密碼、私鑰、網路拓樸、設備序號或完整歷史對話。

## 10. 續接方法與待確認資料

1. 先讀本計劃、來源查核與狀態表，再檢查 `git status` 及遠端提交。不得因其他工作樹有較新日期就取代已固定的基準。
2. 從狀態表第一個未完成且依賴齊備的階段開始；先核對已存在產物與證據，避免重做。
3. 可獨立進行唯讀探索、測試與審查，但由主代理核對結果、限縮提交範圍並統一推送。
4. 優先從既有設備紀錄定位 Berry，不掃整個網段、不停用 SSH 主機金鑰檢查、不猜密碼。舊 IP 只能當候選，登入後仍須核對。
5. 後續硬體階段需要目前的板號／PCB／DDR、UART 端點、受控插座、專用 SD 身分，以及允許使用且已備份的 eMMC 範圍；原生 eMMC 啟動及 EMAC 擴充板另行確認。

上述資訊不全時，可以完成 N1 的離線部分，但不能自動重置、部署救援卡或開始破壞性故障注入。
