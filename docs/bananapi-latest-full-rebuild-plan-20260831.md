# Banana Pi 全系列最新映像重建與替換計畫

日期：2026-08-31

來源分支：`bpi-integration-20260829`

BSP 整合基準提交：`8893355b34efc97a1e7677c6541beb177ec014e1`

實際建置提交：以執行工具時的已推送乾淨 `HEAD` 為準，必須包含上述 BSP
整合基準與本計畫的受控建置工具。工具會把完整提交、Git tree、矩陣
SHA-256、`userpatches` SHA-256 及主機工具資訊寫入建置資訊清單，不再把
「BSP 整合完成點」與「可執行建置工具提交」混為同一個提交。

## 一、目標

以全系列整合分支的最終提交重新建置所有目前具備 L2 可重建條件的 Banana Pi 板卡，產生精簡命令列版與 XFCE 桌面版映像。每張板卡的新矩陣必須完成原始映像唯讀內容檢查、XZ 串流檢查及 SHA-256 驗證後，才可以同檔案系統內的可回復交易替換中央交付目錄舊矩陣。此流程保證中斷後可依交易狀態回復，不把兩次目錄改名誤稱為單一步驟原子交換。

本作業不得先刪除唯一舊映像。新矩陣失敗時保留舊矩陣與可重現日誌；新矩陣通過後才移除該板舊矩陣與工作目錄中的重複映像。

## 二、範圍

- 44 個非 EOS 的 L2 產品板卡：41 個板卡各建置五個發行版、兩種映像，共 410 個映像。
- `bananapicm6`、`bananapif3`、`bananapism10`：RISC-V 64 位元不支援 Bookworm，各建置四個發行版、兩種映像，共 24 個映像。
- `bananapim4zeroemac`：作為 M4 Zero 的獨立功能變體，建置十個映像。
- 預定最新矩陣合計 45 個目錄、444 個 `.img.xz` 與 444 個同名 SHA-256 校驗檔。

`bananapir1` 已是 `.eos`，只保留於歷史封存區，不重新包裝成現行最新支援映像。中央最新矩陣以 `bananapim4zeroemac` 取代原本 R1 所占的目錄位置。

下列三個 L0 產品板卡不產生會誤導使用者的 donor 映像：

- `bananapicm2`：目前只有 R2 Pro 軟體參考，缺少專屬模組與載板 DTS。
- `bananapim2c`：需要可攜 Unisoc／Yocto 來源、修補序列與受控簽署鏈。
- `bananapim4super`：目前只有 ArmSoM Sige3 donor 設定，缺少專屬硬體資料與 DTS。

## 三、建置規則

1. 每板第一個 Trixie 精簡映像使用 `ARTIFACT_IGNORE_CACHE=yes` 與
   `CLEAN_LEVEL=make-kernel,make-uboot,make-atf,make-crust`，清理並重新產生
   該板實際使用的 U-Boot、Kernel、ATF、Crust 與板級套件。
2. 同板其餘發行版可使用第一個映像產生的有效來源與套件快取，避免無意義地重複編譯相同核心十次。
3. 命令列映像使用 `BUILD_MINIMAL=yes`；桌面映像使用 XFCE 與 `DESKTOP_TIER=mid`。
4. 新原始映像先以唯讀 loop 裝置掛載根檔案系統，確認 `armbian-release`、
   精確 `BOARD`、發行版、核心分支、映像類型、來源提交、矩陣雜湊、
   `userpatches` 雜湊、固定建置環境雜湊與非空白開機目錄；`EXIT`、`INT`、`TERM`、`HUP` 都必須
   以有限重試卸載並解除 loop 裝置；若短暫占用未在重試期間解除，保留現場並判定失敗，不使用強制或延遲卸載掩蓋問題。
5. 原始映像通過後壓縮成 XZ，重新計算 SHA-256，執行完整 `xz -t`，然後移除原始映像。
6. 每板所有項目完成前，新檔只放在同檔案系統的暫存目錄；不得覆蓋中央舊矩陣。

## 四、空間與替換規則

- 中央目錄：`/media/pi/SMCI/bpi/google-drive-upload/2026/2026.08`。
- 逐板完成後，以 `prepared`、`old-moved`、`new-installed`、`verified`、
  `committed` 五階段可回復交易替換；每階段狀態先以暫存檔寫入，再於同檔案系統
  改名提交。交易狀態必須精確綁定來源、矩陣與建置環境，缺少或毀損時保留現場並停止。
- 中斷續跑時若回退目錄存在，新正式矩陣通過完整來源、板型、檔名、數量、
  SHA-256 與 XZ 驗證才可完成提交；否則先恢復舊正式矩陣。
- 若交易狀態存在但正式與回退目錄都不存在，工具必須停止並保留現場，
  不得猜測或刪除其他目錄。
- 正式目錄再次通過數量、檔名、SHA-256 與 XZ 檢查後，才刪除回退目錄。
- 每個新項目完成暫存後，只移除該次 UUID 精確產生的原始 IMG 與同名附檔；不得以板名廣泛刪除其他候選或證據。其他歷史重複輸出只在 444 個映像全量驗收及磁碟盤點完成後，依清冊移除。
- 被版本化政策測試引用的歷史證據，必須等新契約改指最新產物並通過回歸後才可刪除。
- 快取只刪除明確可重建的失效項目；固定下載來源、私有材料與唯一證據不納入自動清理。

## 五、續跑與失敗處理

- 工具以實際建置提交建立固定狀態目錄，逐映像標記綁定 BSP 基準、建置
  提交、矩陣、`userpatches`、交付目錄、板型、分支、發行版、映像類型、
  固定容器 digest、主機工具形成的建置環境雜湊、壓縮檔名、精確建置 UUID、
  日誌與 SHA-256。建置提交必須已存在於指定遠端追蹤分支。
- 全工作樹共用互斥鎖，直接執行 `compile.sh` 與受控矩陣建置不得同時寫入共用輸出目錄；映像名稱只由本次 UUID 的 Armbian 內部日誌取得。
- 中斷後重新執行會重驗已完成項目，從第一個缺少或失敗項目續跑。
- 任一映像建置、掛載、壓縮或校驗失敗，該板不替換舊目錄。
- 失敗不阻擋其他獨立板卡繼續建置；每次執行重寫本輪摘要，避免把舊失敗
  誤認成現況。
- `INT`、`TERM`、`HUP`、管線中止與強制終止狀態不得被當成一般板卡失敗；工具記錄中斷後立即停止。
- R1 只會在 45 個新目錄全部建置與驗證成功後移入歷史封存區，不會在
  新矩陣建置前改變正式交付內容。封存前必須重驗預設矩陣正好為 45 個目錄、444 個映像，且來源與封存目的地位於同一檔案系統。
- 整個矩陣完成後重新執行全系列程式回歸、全量 XZ／SHA-256 驗證與磁碟盤點，再提交並推送結果文件。

## 六、完成條件

1. 45 個可建置目錄的每個預期矩陣項目都有本次來源提交的成功建置日誌。
2. 中央目錄只保留各板最新矩陣，不保留被新版取代的舊映像。
3. 444 個壓縮映像全部通過 SHA-256 與 XZ 串流驗證。
4. 三個 L0 板卡保留正確阻擋原因，不以 donor 映像冒充完成。
5. 建置摘要、失敗摘要、來源提交、產物數量與空間變化可追蹤。
6. 自動化工具、測試與最終結果已提交並推送至 `bpi-integration-20260829`。

## 七、2026-09-04 來源契約修正與全量重啟

來源提交 `b82ce7900208d32dc82f6462f0b6990fd259839a` 的四線重建在完成
20 張板卡、產生 202 個壓縮映像後，`bananapim64` 的第一個 Trixie 精簡
映像於 U-Boot 修補階段停止。調查確認板卡設定將 U-Boot 固定於
`866ca972d6c3cabeaf6dbac431e8e08bb30b3c8e`，也就是 `v2024.01`，但未同步
固定補丁目錄，因而誤用 `v2026.07-sunxi64` 中的新版 MMC 與 A523 專用修補。
這是來源設定錯配，不是 loop 裝置、下載、磁碟空間或編譯主機的暫態錯誤。

修正採用 `v2024.01/board_bananapim64` 專用補丁目錄，只納入 M64 既定的
A64 648 MHz DRAM 修補，不把 A523、H616 或其他 SoC 修補套到 A64。隔離測試
已關閉 artifact cache，從固定提交重新完成 ATF、Crust 與 U-Boot 2024.01
編譯，並成功產生
`linux-u-boot-bananapim64-current_2024.01-S866c-Pc536-H0021-V7117-B83dd-R448a_arm64.deb`。

完整 Banana Pi 測試集合共 526 項通過。測試過程另發現 P2 Zero 補丁郵件
標題含非 ASCII 文字，已將標題收斂為技術識別字 `sunxi: BPI-P2-Zero`，中文
補丁說明維持不變，避免郵件式補丁解析器失敗。

由於來源提交、建置環境雜湊及最終驗證器要求整個矩陣一致，舊提交的
202 個映像只能保留為中止證據，不得與修正後產物混合。四條舊建置線及
其殘留容器已停止；保存摘要、日誌與必要雜湊後，清除舊映像並以包含本節
修正的乾淨已推送提交重新建立 45 張板卡、444 個映像。
