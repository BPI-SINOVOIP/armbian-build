**為何本機測試與自檢沒有擋住**

受查版本的 `verify()` 主要核對整包 SHA-256、成員名稱／大小／雜湊、路徑安全；有提供 root／boot UUID 時再核對 ext4 UUID。它的結果明確標示 `scope=offline-archive-integrity`、`hardware_validation=pending`。這個檢查範圍本身有寫出限制，但不能拿其 `passed` 當成 Titan 接受封裝的證明。

本輪以暫存目錄作了具體反例：建立只有 `env.bin`、內容 `bytes(5)` 的 ZIP；建立自洽的 artifact SHA-256 與單一 `archive_members` manifest，指定 `board=bpi-cm6`、`storage=emmc`，不提供 UUID；呼叫受查版本 `verify()`，仍得到 `status=passed`、`scope=offline-archive-integrity`、`hardware_validation=pending`。暫存資料已清除，沒有修改測試。這證明它沒有強制要求 Titan 必要控制檔，更不會執行分區匹配。

目前可見的覆蓋缺口如下：

- `archive_members` 由輸出自身推導；自洽清單只能證明「收到的內容等於自己宣告的內容」，不能證明官方需要的內容都有提供。
- `source_reference()` 能阻擋官方輸入遭竄改，但 `build()` 後續仍能刪除成員、改寫 YAML 或替換分區欄位；來源鎖不等於輸出契約。
- `test_layout_uses_official_units_and_media_headers` 明確要求 eMMC 選擇 eMMC bootinfo，固化了實作假設；沒有取得 Titan 或官方 eMMC 路徑來證明這個假設。
- 測試的來源 fixture 與 ZIP fixture 都由程式自行產生，沒有比對真實官方 ZIP 的完整成員集合；ext4 UUID 正向測試甚至只用 bootfs／rootfs 兩個成員。
- 沒有根據真實 `getvar` 回應演算候選表、檢驗所有檔案引用或呼叫 Titan。SD 的 GPT CRC、偏移與載荷測試雖有價值，覆蓋的是另一條交付路徑。
- `evidence/audit_candidates.py` 檢查 rootfs、服務與安裝入口防護，沒有 Titan 消費者行為。既有本機回歸通過不等於 USB 協定、分區匹配、寫入、冷開機通過；若將同一批測試搬到 CI，也不會自動填補這個缺口。

**建議驗證順序**

1. 固定接收端 Titan 精確版本、實際選取 ZIP 的 SHA-256、板型與儲存裝置，先保存未截斷的完整日誌。以同工具、同板確認官方參考是否能進入正確分區匹配，避免把主機設定或版本差異混入封裝結論。
2. 以官方原始控制檔與完整成員集合為相容基準，保持 bootfs／rootfs 及六個既有二進位載荷不變；記錄 `mtd-size`、`blk-size`、模板展開後名稱、實際選中的分區表與媒體。完整結構可以減少變因，但不能因此開放非目標媒體的實際寫入。
3. 將固定 `relate_partition`、候選表／SPI 載荷缺少、bootinfo 替換分開作對照。若只能一次回復全部官方結構，可以先解決使用問題，但要明確保留「尚未分離唯一根因」的結論。
4. 若仍不能匹配，再逐一比較 `genimage.cfg`、顯式目錄成員、順序與 ZIP extra；目前沒有足夠證據把它們排在控制檔差異之前。不要把不存在於官方 ZIP 的 `platform.json` 補成新的必要檔案。
5. 補本機契約測試：必要成員集合、YAML 與分區檔引用閉合、官方候選表選擇的受控回應案例、缺檔／未知媒體拒絕。若沒有可核對的 Titan 匹配規格，測試名稱與交付說明應限定為封裝契約檢查，保留 Titan 實測待辦。

分區表選擇不再為空，只代表修復了目前失敗階段。eMMC 交付仍須獲得實際媒體選擇、完整燒錄、斷電冷開機及 Armbian 環境證據；GPU、AI 與多媒體驗收另依板上證據完成。本輪不能替這些項目宣告通過。
