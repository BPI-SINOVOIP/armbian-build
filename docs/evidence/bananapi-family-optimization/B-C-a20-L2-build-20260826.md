## 結論

## L2 守門範圍

1. 檢查候選矩陣、中繼資料、映像來源提交、來源樹及建置時驗證設定雜湊一致。
2. 分開記錄映像來源提交、驗證器提交、建置時政策及 L2 驗證政策，避免把守門程式更新誤作映像重建。
3. 檢查 IMG／XZ 大小、SHA-256、壓縮串流及解壓同一性。
4. 以唯讀 loop 與 `mount -o ro,noload` 檢查映像，不執行映像內程式。
5. 檢查核心、initrd、`overlay_prefix=sun7i-a20`、板級 DTB model、compatible 與必要節點。
6. 檢查 SD 控制器為 4-bit，並確認 Ethernet、HDMI、I2C、SATA、SPI 與板上 USB 節點處於啟用狀態。
7. 檢查 AHCI、Lima、Sun4i DRM、Cedrus、Crypto、MMC、Ethernet、I2C、SPI、PWM 及 USB gadget mass-storage 核心設定。
8. 檢查 `gpiod`、`i2c-tools`、`python3-libgpiod`、`python3-spidev` 與 `v4l-utils` 已安裝。
9. 檢查 U-Boot 套件版本及 payload MD5，並比對 IMG 8 KiB 偏移的實際位元組與 `u-boot-sunxi-with-spl.bin` 完全相同。

## 驗證政策修正紀錄

首次守門揭露兩項驗證假設與實際 Sunxi 封裝格式不同：

- A20 U-Boot 已內建預設 `fdtfile`，`armbianEnv.txt` 沒有覆寫時屬正常；若有覆寫，驗證器仍要求來源路徑或封裝 basename 精確相符。
- 核心來源樹的 DTB 位於 `allwinner/`，Debian 套件在 `/boot/dtb/` 安裝 basename；驗證器會依序檢查兩種合法位置。
- A20 顯示引擎是根節點 `/display-engine`，不是 `/soc/display-engine`。兩張映像內 DTB 反編譯結果一致，驗證設定已校正後重新執行完整 L2 守門。

上述修正均有回歸測試，且驗證狀態同時保存建置與驗證政策雜湊。

## 已知限制與 L3 門檻

- 每張板至少執行 30 次完整斷電冷啟，保存 UART 全程日誌及失敗率。
- 驗證 SD 讀寫、SATA 儲存與校驗、GBE 吞吐及長時間封包壓力。
- 驗證 HDMI 多解析度、Lima OpenGL ES、Cedrus V4L2 解碼與 CPU 使用率。
- 驗證 USB host、可用 OTG 埠的 gadget mass-storage、GPIO、I2C、SPI、UART 與 PWM 實體迴路。
- `bananapipro` 另須驗證板載 Wi-Fi、eMMC 與板卡特有介面；不能由 `bananapi` 結果推論通過。
