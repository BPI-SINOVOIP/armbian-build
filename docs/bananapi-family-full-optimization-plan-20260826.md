# Banana Pi 全系列 Armbian 最佳化與映像交付計畫

日期：2026-08-26

修訂日期：2026-08-28

工作分支：`bananapi-family-optimization-20260826`

基線提交：`006e236b6`

## 一、目標

以 Banana Pi M4 Zero 與 M4 Berry 已建立的 DDR、硬體加速、40-pin、映像矩陣及實機證據流程為基礎，重新檢查本分支全部 Banana Pi 板卡，依 SoC 家族修正共用問題，為尚未完整最佳化的板卡建立可重現映像與驗證紀錄。

本計畫的完成標準不是「映像可以產生」，而是依證據逐級達成：

1. 板卡設定、來源、核心、U-Boot、DTB 與映像配置可追溯。
2. 代表性 CLI 映像可完整建置並通過離線內容檢查。
3. 實機可完成冷啟動、記憶體、儲存、網路、USB、顯示與重新啟動驗證。
4. 依 SoC 能力驗證 GPU、視訊、密碼引擎及 40-pin I/O，不以裝置節點存在代替功能成立。
5. 通過代表性映像後，再產生五個發行版的 CLI／XFCE 十映像矩陣。
6. 每一批次保留程式提交、建置參數、日誌、雜湊、限制與實機證據，並推送至遠端分支。

## 二、範圍與現況

本分支共有 48 個 Banana Pi 板卡定義：

- 正式設定 `.conf`：12 個。
- 社群設定 `.csc`：14 個。
- 開發中設定 `.wip`：21 個。
- 停止支援設定 `.eos`：1 個。

`.conf` 只表示目前可由一般流程選用，不等於全部硬體功能已驗收；`.csc`、`.wip` 與 `.eos` 不得因建置成功而改寫為正式支援。

### 2.3 執行修訂原則

- `config/bananapi-optimization-status.json` 與機械產生的全板稽核是目前證據等級的唯一登錄來源；個別文件或未追蹤產物不得單獨提升等級。
- 固定來源與板級 U-Boot、核心、DTB 或模組元件可重建，只足以進入 L1；必須另有完整整碟映像及唯讀內容守門才可進入 L2。
- 需要私有遠端、簽署金鑰、不可確認再散布權的二進位或不可重放本機差異時，先完成可自動化的來源稽核與拒絕守門，狀態維持 L0 或 L1。
- `.eos` 板卡的既有映像若通過完整性與唯讀內容檢查，只能標示「歷史封存證據」；不得推論目前來源仍可重建、目前分支仍受支援或硬體已驗證。

## 三、證據等級

每個板卡只能依實際證據標示下列最高等級：

| 等級 | 名稱 | 必要證據 |
| --- | --- | --- |
| L0 | 已盤點 | 板卡設定、來源、目標分支及已知缺口已記錄 |
| L1 | 元件可建置 | 固定來源的板級 U-Boot、核心、DTB、模組或必要啟動元件已重建並保存日誌與雜湊；不得宣稱已有完整映像 |
| L2 | 軟體候選 | 完整整碟映像已建置，且壓縮串流、SHA-256、唯讀掛載、套件、核心設定、DTB、模組及啟動載荷檢查通過 |
| L3 | 實機候選 | UART 冷啟動、登入、記憶體、儲存、網路、USB 與重啟基本驗證通過 |
| L4 | 功能最佳化 | 板卡具有的 GPU、VPU、Crypto、Wi-Fi、Bluetooth、40-pin 與顯示介面完成實測 |
| L5 | 發布候選 | 樣本數、長時間壓力、十映像矩陣、文件、限制與雜湊完整 |

任何缺少實機的工作最多只能標示 L2。單片暖啟動成功不能代表冷啟動、跨批次或量產成立。

## 四、共同最佳化基線

### 4.1 啟動與儲存

- 固定 U-Boot、ATF、韌體、核心及修補檔來源與提交碼。
- 核對 SPL／TPL／FIP／PAC／原始磁區寫入位置，不跨板共用未證實的配置。
- 驗證 SD、eMMC、NVMe、SATA 或 NAND 等板載介面；針對不同 eMMC 廠牌採保守時序並記錄退讓原因。
- 驗證完整斷電冷啟動、暖重啟、關機及非正常斷電後檔案系統恢復。

### 4.2 核心與硬體加速

- 確認 CPU 頻率、調速器、熱區、風扇與降頻行為符合硬體規格。
- 圖形測試必須記錄實際渲染器，排除 `llvmpipe` 或其他軟體路徑。
- 視訊測試必須記錄格式、解析度、幀數、裝置中斷、執行時間及錯誤，不以 `/dev/video*` 存在作為硬解證明。
- 密碼引擎須同時驗證正確性、硬體統計與回退路徑。
- vendor 核心功能與主線核心功能分開記錄，不以 vendor 成果推論主線已支援。

### 4.3 網路與無線

- 驗證每個 Ethernet 埠的協商速率、雙向吞吐、長時間傳輸與重新插拔。
- 路由器板卡另外驗證交換器、SFP、WAN／LAN 分工、封包轉送與硬體卸載。
- Wi-Fi 須完成掃描、連線、位址取得、雙向傳輸與重新連線；只掃描到基地台不算完成。
- Bluetooth 須完成控制器初始化、掃描、配對及至少一種資料或音訊傳輸。

### 4.4 USB、顯示與 40-pin

- 逐埠驗證 USB 2.0／3.x、Type-C 角色、OTG 與供電限制；有裝置模式的板卡驗證 `g_mass_storage` 或 ConfigFS 等標準路徑。
- 驗證 HDMI、DSI、eDP、MIPI CSI 等板載介面實際輸出或擷取，不只檢查 DTB 節點。
- 建立每板實體 pin 對照，驗證 GPIO、I2C、SPI、UART、PWM 及中斷。
- 核心介面以 `libgpiod`、`i2c-tools`、`spidev` 等標準介面為主；BPI-WiringPi2 與 RPi.GPIO 另列相容層結果。
- 裝置權限採群組與 `0660`，不使用全域可寫的 `0666`。

## 五、映像策略

### 5.1 代表性候選

每個新板卡或新家族先建置 Debian 13 `trixie` CLI 候選：

```bash
./compile.sh build BOARD=<board> BRANCH=<branch> RELEASE=trixie \
  BUILD_DESKTOP=no BUILD_MINIMAL=yes KERNEL_CONFIGURE=no \
  EXPERT=yes COMPRESS_OUTPUTIMAGE=xz
```

候選映像通過 L2 後才進入實機驗證。無硬體時可繼續完成軟體修正與建置，但狀態維持 L2。

### 5.2 十映像矩陣

達到 L3 且沒有阻斷性問題的板卡，完整建立下列矩陣：

| 發行版 | CLI／精簡 | XFCE |
| --- | --- | --- |
| Debian 12 `bookworm` | 是 | 是 |
| Debian 13 `trixie` | 是 | 是 |
| Ubuntu 22.04 `jammy` | 是 | 是 |
| Ubuntu 24.04 `noble` | 是 | 是 |
| Ubuntu 26.04 `resolute` | 是 | 是 |

不支援特定發行版或架構時，必須保存明確的跳過原因，不得以空白或失敗計數代替。

### 5.3 空間與產物管理

工作磁碟可用空間會隨隔離快取與完整映像建置大幅變動，不能同時保留所有板卡的十個未壓縮映像。採下列規則：

- 正式交付矩陣預設同時保留 `.img` 與 `.img.xz`；不得只因已有壓縮檔就自動移除 `.img`。
- 只有明確標示為失敗、拒絕、已被正式候選取代或單次校準的產物，才可在證據摘要與雜湊保存後移除。
- 每批映像放在 `output/images/2026.08/bananapi-<board>-optimized-candidate/`。
- 每批保留建置參數、核心與 U-Boot 套件版本、檔案雜湊、檢查摘要及硬體驗證範本。
- 大型映像不加入 Git；Git 只追蹤來源、工具、測試、計畫、結果摘要與可重現中繼資料。
- 共用 `/media/pi/SMCI/armbian/bpi-v26.2.1/cache` 永遠視為唯讀下層；只能在卸載、路徑、程序與容器檢查通過後，刪除單一候選專用的 OverlayFS 上層。
- 未整合工作樹、原始碼、PAC、原廠文件、正式映像、正式證據與實機日誌不得納入自動清理。
- 大型 Yocto／Buildroot 中間目錄只在來源、設定、發布產物與重建方式已完整封存後分批回收，每批須留下路徑、估算容量、保留項與刪除結果。

## 六、執行階段

### 階段 0：先推送本計畫

本文件必須單獨提交並推送，之後才開始修改盤點工具或板卡程式：

```bash
git add docs/bananapi-family-full-optimization-plan-20260826.md
git commit -m "計畫：建立 Banana Pi 全系列最佳化流程"
git push -u origin bananapi-family-optimization-20260826
```

### 階段 1：建立可續跑盤點與守門工具

1. 自動列出 48 個板卡設定、狀態、SoC 家族、核心目標、U-Boot、DTB 與架構。
2. 比對既有最佳化文件、測試、映像及硬體證據。
3. 產生可重現的 TSV 與 Markdown 狀態報告。
4. 新增回歸測試，防止漏板、重複板卡、欄位缺失或把 `.wip` 誤列正式發布。
5. 推送盤點工具、測試與初始全板報告。

### 階段 2：執行 A 批次 Meson 四板

依序處理 `bananapim5`、`bananapim2pro`、`bananapicm4io`、`bananapim2s`：

1. 比對既有 CM4 與 M5 eMMC 修正，確認是否已在本分支生效及是否應由板級修正提升為安全的家族共用邏輯。
2. 檢查 current 核心與 U-Boot 的儲存時序、USB 角色、顯示關機、GPU、VPU、網路與 overlay。
3. 每板先建置 Trixie CLI，執行 L1／L2 守門。
4. 有可連線硬體的板卡執行 L3／L4；無硬體者產生完整測試包並列入最後待協助清單。
5. 已達 L3 的板卡建立十映像矩陣；未達 L3 的板卡保留單一候選，不擴大成容易誤用的發布矩陣。
6. 每板或每個不可分割的家族修正單獨提交並推送。

### 階段 3：正式支援板卡與成熟 Allwinner 板卡

1. 先處理 B 批次中的正式設定板卡，再處理 C 批次。
2. 同一 SoC 家族共用核心修正，但 DTB、腳位與啟動媒體逐板驗證。
3. 已有舊版映像者先比對核心、U-Boot、韌體與已知問題，不因檔案存在而跳過重建。
4. 每個家族先通過一個代表性板卡，再平行展開同家族其餘板卡。

### 階段 4：網路板卡、Rockchip 與特殊 BSP

1. D 批次以網路與啟動媒體為主要門檻，不套用桌面板卡的相同宣告。
2. E 批次分開記錄主線與 vendor 結果，NPU、GPU、VPU 與顯示各自驗證。
3. F 批次先解決來源可重現性與封裝鏈；需要簽章、PAC 或專有韌體者只交付可依法重建的部分。
4. `.wip` 只有在實機門檻與維護責任明確後才評估升級狀態。

### 階段 5：全系列回歸與發布資料

1. 重新產生全板狀態報告，列出每板最高證據等級與剩餘缺口。
2. 對所有產物執行 SHA-256、`xz -t`、唯讀內容與檔名／中繼資料一致性檢查。
3. 產生繁體中文公開發布說明、燒錄與驗證文件；必要的產品名稱與命令保留原字串。
4. 明確分開「已完成」、「軟體候選」、「需要硬體」與「受專有元件阻擋」。
5. 推送最後報告與每個階段的提交碼，不依賴大型映像或未追蹤日誌作為唯一證據。

## 七、第一批驗收項目

Meson 四板至少完成下列共同檢查：

- U-Boot、核心與 Trixie CLI 建置成功。
- 映像可解壓、雜湊一致、分割區可唯讀掛載。
- 映像內板名、DTB、核心、模組、韌體與網路設定符合目標板。
- SD 與 eMMC 的裝置樹時序、匯流排寬度及最高頻率有可追溯依據。
- USB 各埠角色與 Type-C／OTG 能力有設定與實機證據，或清楚標示待測。
- DRM 關機逾時、CPU 電源關閉、重新啟動及關機訊息完成回歸。
- GPU 渲染器、視訊解碼介面及格式逐項記錄，不能以功能名稱推論可用。
- Ethernet、Wi-Fi、Bluetooth 與 40-pin 按板卡實際配備驗證。
- 實機至少執行記憶體、儲存與 CPU 混合壓力；正式候選另需長時間與多次冷啟動。

## 八、提交與續跑規則

- 計畫、盤點工具、家族修正、單板修正、映像驗證與實機證據分開提交。
- 每一個可獨立檢查的階段完成後立即推送，不把所有工作壓成單一提交。
- 建置摘要保存成功、失敗、跳過、命令、起訖時間及第一個有效錯誤。
- 重新執行時以雜湊及完整守門結果判定是否跳過，不只比對檔名。
- 不修改或回復其他工作樹中的既有未提交內容；本計畫只在獨立工作樹執行。
- 若板卡缺少硬體、簽章金鑰、不可再散布韌體或必要介面，先完成其餘可自動完成工作，最後彙整一次請求協助。

## 九、完成判定

本計畫不以「48 板全部標示完成」作為形式目標，而以每板具有真實、可重現、無誤導的最高證據等級為準。整體交付完成時必須同時具備：

1. 48 個板卡皆有盤點結果、執行批次、最高證據等級與下一項具體工作。
2. 所有在現有來源、授權與主機條件下可建置的板卡完成 L1／L2；受私有來源、授權、簽署鏈或不可重放差異阻擋者，具有可重現的拒絕證據、修正判斷與明確升級條件。
3. 所有可取得實機的板卡完成對應 L3／L4，未取得實機者不得宣稱硬體通過。
4. 達到 L3 的板卡完成其適用的映像矩陣與交付文件。
5. 所有程式、工具、文件與結果摘要已分階段推送。
6. 最後只保留一份需要使用者協助的硬體、連線、授權或外部發布清單。

## 十、執行進度
